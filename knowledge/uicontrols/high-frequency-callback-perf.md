# 高频回调性能规范：拖动/触摸回调里**禁止全量刷新**

> 检索导引：问「拖动卡顿·滑动很卡 / 高频回调里顺手刷了整页 / 触摸事件被合并丢弃 / 掉帧怎么量化」→ 本文；列表封面类的另一路优化见 `uicontrols/listview-image-cache.md`。
> 检索词：滑动很卡 / 拖动卡顿 / 滑块拖不动 / 拖动掉帧 / 全量刷新 / updateUi 每次都调 / 高频回调 / setText 刷一整屏 / 运动事件被丢弃 / 触摸事件合并 / 事件被吞 / 回调太慢 / 优先级 / 拖动响应延迟 / CPU 占用高 / 掉帧 / 帧变化率 / A/B 量化口径。
> 案例：`projects/translate/tdesign-miniprogram`（2026-09-17 真机实测；报告 `SLIDER_PERF.md`）。设备条件：Z21 同型板 1024×600、**无 GPU / 纯软渲染**；设备 IP 用参数传入（`--dev <IP>:5555`）。
> 适用：任何**高频回调**——`onProgressChanged_*`（拖动）、滑动/长按、逐帧定时器、以及被它们间接调用的「一次性刷全页」函数。

## 0. 一句话

**回调里只刷「这次真正变了的那一个控件」**；任何「顺手把整页状态同步一遍」的写法，在拖动/触摸这种每帧一次的回调里都会把小问题放大成卡顿——**一次回调 86 次 GUI 调用 = 事件被合并丢弃**。

## 1. 症状与真机反馈

> 原话（2026-09-17 客户真机反馈）：「滑块页面滑动很卡，**但是禁用标签这个进度条流畅度很高**」。

同一页、同样尺寸的 4 条 `seekbar`，**3 条卡、1 条顺**——差异不在控件，在**回调重量**。「同页同类控件手感不一致」是这条铁律最好认的信号：先去比两个回调**各写了几次控件**。

## 2. 根因（代码级，已核对）

3 条 seekbar 的拖动回调走了**整案例全量刷新**：`onProgressChanged_SeekBase` 里 `updateUi()`（整页同步，静态展开后单次约 **38 次控件写入**：21 `setText` + 9 `setSelected` + 4 `setVisible` + 4 条滑块值文本），末尾还调 `updateS3()`（再展开约 **48 次**：badge 8 / tag 12 / closeTag 6 / progress 11 / count-down 11）：

- **一次拖动事件 ≈ 86 次 GUI 调用**，其中和滑块**毫无关系**的 16 个页面状态全被重刷一遍。
- 对照组（那条「禁用」滑块）的回调**只写 1 个 textview**（状态行）→ 同样的注入毫无压力。

**真机日志佐证**（同一次 boot、同一套注入，`logcat` 数回调次数；工具自带约 95 步滑动）：`touch swipe ...` 往返拖动下，**重回调条回调 29 次 vs 轻回调（对照）90 次** → **重回调导致运动事件被合并/丢弃**（95 步只处理了 29 次），这本身就是「卡顿」的机制，不是「画得慢」这么简单。

## 3. 改法（最小改动，语义不变）

1. **抽出细粒度同步函数**：新增只刷该类控件自身值的函数（案例 `syncSeekValues()` 只刷 4 条滑块的值 textview），并**值没变就跳过**（`step=10` 那条本来就会有重复回调）。全量函数里原来那几段改成调它。
2. **高频回调改轻路径**：拖动回调 = 「细粒度同步 + 状态行」，**不再调全量刷新**；其它控件状态本来与滑块无关，初始化 / 页面切换时**全量刷一次兜底**即可。
3. **文案没变不 setText**：重复文案视觉无变化却触发整行重绘。日志（`LOGD`）保持无条件输出——真机取证要靠它。
4. **双平台同源**：两份平台目录的 `mainLogic.cc` **改动逐字节一致**（案例用 `difflib` 逐行核对），避免手改两份漂移。
5. 注释只用 **ASCII 标点**（避开 `check_all` 的特殊字符黑名单）。

## 4. A/B 量化（真机实测）

**量具口径（可复用）**：注入用工具自带 `touch play <rec>` 回放（`touch raw` 参数上限 8 个，而一帧 MT-B DOWN 要 9 项）→ 录制文件 = **1 帧 DOWN + 20 帧 MOVE + 1 帧 UP = 一步一帧的 20 步沿轨拖动**，往返合并成一个文件、`play -r N` 连放；**每次拖动前先 tap 到起点把拇指归位**（否则开头 DOWN 帧自身就是一次跳变，会把「响应延迟」测成 0）。**计时全在设备侧**（adb 往返 30–60ms 抖动与所测的量同量级）：`T0/T1` 取 `/proc/uptime`（10ms 精度），CPU 取 `/proc/<zkgui pid>/stat` 的 `utime+stime`（jiffies），采样循环以 `kill -0 <play pid>` 为准。**视觉响应延迟**读**当前显示的那半块 framebuffer**（双缓冲板 `pan` 在 0/半高 间翻），取覆盖「滑块拇指 + 值标签」的横带并 md5，判据 = **同一半块相对上次 md5 变了 = 画了一张新帧**。两个步进速率：`40ms/步`（840ms 慢拖，能分辨每一步）与 `12ms/步`（240ms 快拖，≈真实触摸屏 80Hz 上报率）。

**三条结论**（每格 6 次拖动取中位，重回调 vs 同页被认可流畅的轻回调对照组）：

1. **CPU 降一个数量级**：慢拖 **73.8% → 7.3%**（÷10.1）、10 连拖 **74.4% → 6.9%**（÷10.8）、快拖 **91.3% → 19.2%**（÷4.8）。
2. **响应快一倍以上**：慢拖 **250 → 135 ms**（-46%），快拖 **383 → 134 ms**（-65%）；快拖帧变化率 **0.27 → 4.13 fps（×15）**，每 20 步画出的帧数 **0 → 3**（不再「攒到最后一次性重绘」）。
3. **滑块不再特殊**：改后与轻回调对照组**已同档**（CPU 7.3% vs 6.9%、延迟 135 vs 195 ms、每拖动帧数 3 vs 3）；对照组数字全程没变（噪声内）→ **不是量具漂移**。

> 口径提醒：`12ms/步` 下可分辨帧数上限受**采样器 25ms/次**限制，只用于**同条件横比**，不能当绝对帧率；能分辨每一步帧数的是慢拖（40ms/步）口径。
> 语义回归（像素级）：同一 boot、同一套注入抓「值标签」区域 md5 —— 3 条改动滑块的**值文本都跟随**，未改动那条与改前**逐字节一致** ⇒ **轻量化不改变语义**。

## 5. 自查清单（写/改任何高频回调时打勾）

- [ ] 拖动/滑动/触摸回调里**没有**调用「整页同步」函数
- [ ] 回调只写**这次变化的那一个（少数几个）控件**
- [ ] `setText` 之前**比过值**，文案相同就跳过（日志照打）
- [ ] 全量刷新只在**初始化 / 页面切换 / 低频动作**里跑一次兜底
- [ ] 有个「同页同类的轻回调」当对照吗？没有就现场造一个（同条件横比才说明问题）
- [ ] A/B 用**设备侧**计时与 `stat` 取样，别用 adb 往返测毫秒

## 6. 同类隐患（体检时顺手查）

| # | 位置 | 结论 / 处置 |
|---|---|---|
| 1 | 逐帧定时器（如 100ms 节拍） | ✅ 只要节拍内**不调全量刷新**就安全；把刷新压到所需频率（案例：倒计时「秒变才刷」压到 1Hz、toast 只在到点 hide、动画帧确实每步都变） |
| 2 | **全量同步函数挂在每个「小动作」末尾** | ⚠ 常见毛病：任何按钮/开关/复选框动作都顺带同步整页（案例实测约 48 次无关控件写入）；低频没人抱怨，但接口一多就是下一个卡顿源 → 按页拆分全量同步 |
| 3 | **空壳回调**（回调体里只有日志、不写状态） | ⚠ 不是性能问题，是**一致性**问题：同名控件在不同页行为不同（拖了画面不动）→ 明确接上数据或标注为纯装饰 |
| 4 | 每帧 `setBackgroundPic` 换图 | ✅ 只要帧图**确实每次都不同**就不算浪费（案例 loading 帧号自增 → 图确实每次都变） |

## 7. 量具自身的三个坑（别「简化」掉）

1. `play -r` 连放时**首趟前没有间隔**（实测每趟耗时不等距，会让后续每个拖动窗口错位）→ 录制文件开头加一帧空 SYN 兜底。
2. 帧变化必须**按半块分别比对**（双缓冲 pan 每帧翻一次）。
3. 采样循环必须**跟随注入进程生命周期**（`kill -0 <pid>`），不能按估算的样本数跑。
