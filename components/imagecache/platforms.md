# imagecache — 平台说明（实测值；没测的一律标「未验证」）

组件：`components/imagecache/`（源码型：`include/ + src/ + example/`）
能力：按**路径**缓存「已解码位图」（权重 LRU + 引用计数 + 锁），专治 listview 刷新/回页时
`setBackgroundPic(path)` 反复解码同一张图导致的 UI 线程卡顿。

> ⚠️ 读法先讲清（不夸大）：本文件的**真机数字来自工程内联基线**
> `projects/iOSStyle-F133/src/core/ImageCache.hpp`（语义与 `zk::ImageCache` 逐行同源，差别只在
> 「装载走回调」+「错误处理不静默」）。**组件形态本身还没在真机上跑过**（见 §5），
> 真机回归属于待办 —— 不要拿下面的数字当成「组件已在真机验证」。

## 2. F133 真机实测（iosstyle 音乐 App，2026-09-23）

板子/形态：F133 真机（800×1280 面板 + rotate 270 → UI 1280×800；内网板，地址从略），整包跑在 `/tmp`，
`/tmp/EasyUI.cfg`：`touchDev=/dev/input/event3`、`rotateScreen=270`、`resPath=/tmp/ui/`。
量法：在 `obtainListItemData_*` 里 `setBackgroundPic()` 前后加临时计时埋点（**验收后已从源码移除**），
量的是**框架解这张 PNG 的 UI 线程耗时**。

### 2.1 单张解码成本（这是「慢」的根）

| 图 | 尺寸 | 单张 `setBackgroundPic` 耗时 |
|---|---|---|
| 推荐列表圆角封面 | 280×280 | **26~65 ms** |
| 榜单 / 搜索列表小图 | 64×64 | **3~4 ms** |

### 2.2 改前 / 改后（同一操作各一次，同一台板）

| 场景 | 改前（无缓存） | 改后（有缓存） | 变化 |
|---|---|---|---|
| **首屏** 6 推荐 + 2 榜单（首次解码，不可避免） | **211 ms**（8 次解码） | **208 ms**（装载 ×8） | ≈持平（**不加速首解，设计如此**） |
| **回页重设同一批封面** | **315 ms**（8 次解码） | **1 ms**（命中 ×8） | **−99.7%** |
| 回页整体的第二批（新路径，首次解码） | 209 ms | 205 ms | 持平 |
| **回页合计** | **524 ms** | **206 ms** | **−61%** |
| **拖动**（推荐/榜单/搜索结果） | 解码 0 条 | 解码 0 条 | 拖动本来不重复解码（工程侧 mark 表挡住） |

读数口径：`hits()` / `loads()` 就是「命中次数 / 解码次数」；改后回页日志（留档
`temp/music_ui/i_return.txt`）：

```
ImageCache 命中 /tmp/cm_riv_rec0_280x280_1.png weight=-5     ← 命中（0ms 上屏）
cover dbg: rec idx=0 setBackgroundPic 0ms ...
ImageCache 装载 /tmp/cm_riv_rec0_280x280_9.png 槽=9/128      ← 新一批（首次解码 37ms）
```

改后进程内存 `VmRSS: 8964 kB`（缓存 8~40 张，槽位上限 128 由 LRU 兜住）。

### 2.3 一次真回归（必须记住的坑）

把搜索页也接上缓存后，真机复现：**第二次搜索结果显示上一批封面**（串图）。
根因：搜索封面原来是**固定名** `cm_cov_sg<i>.png`（换内容不换名），而缓存按**路径**记已解码位图
→ 一 pin 住就永远是旧图。修法：路径带**批号**（`cm_cov_sg<批号>_<序号>.png`，开新搜索删上一批）。
修完全部正常（两批封面不同）。**这是本组件的硬约束：路径必须唯一（含批次/版本）。**

```bash

cd components/imagecache
mkdir -p _t && cd _t
g++ -std=c++11 -O2 -Wall -Wextra -I../include ../example/zk_imagecache_test.cpp ../src/zk_imagecache.cpp -o zk_imagecache_test
./zk_imagecache_test          # 退出码 0 = 全 PASS；加 -v 逐次打印 load/free
```

实测结果（29 项，0 FAIL）：

| 组 | 覆盖 |
|---|---|
| 0~1 | 未配置就 cache → 返 false + lastError（不静默）；configure 幂等 |
| 2~3 | 首批 8 张解码 8 次；**回页重设同一批 → 解码 +0，命中 8 次** |
| 4 | 引用计数：还有一个页面在用就不清；最后一个退出才 releaseAll |
| 5 | 权重 LRU：hot 命中 4 次后不被挤掉，被踢的是最早那张冷图（可指名验证） |

## 5. 已知限制 / 未验证项（选型前必看）

1. **组件形态未做真机回归**：真机数字来自工程内联版（`ui::ImageCache`，直接调 `BitmapHelper`）。
   组件版把装载换成回调、错误处理改为不静默，**语义一致但没在真机跑过**；
   已有工程的替换属于「改运行时行为」，本次任务范围外。下次改工程时顺手回归一次即可。
2. **首解不加速**：只在「同一路径第二次上屏」生效。要让新图也快，只能在**后台线程预热**
   （渲染完顺手 `cache()`）—— 涉及跨线程持有框架资源表，工程侧尚未验证，别默认打开。
3. **路径唯一是硬约束**：见 §2.3。固定名封面（换内容不换名）会串图，必须先改命名。
4. **容量是内存换速度**：`capacity × 单图解码体积`（280×280 BGRA ≈ 300 KB/张，128 槽 ≈ 38 MB 上限）。
   Z20/Z21 那类 36~128 MB 内存板尤其要算账，别无脑加大。
5. **别照抄 `drop_caches`**：HaishiM9 原版 `releaseAll()` 末尾有
   `system("echo 3 > /proc/sys/vm/drop_caches")` —— 全局副作用（把页缓存全倒掉，后续所有文件读更慢），
   且 `system()` 在 UI 线程 fork 一个 shell 本身就是卡顿源。**本组件没有这一句**（组件里也没有 system() 调用）。
6. **只对「每次刷新都会重设的图」有价值**（列表 fill / 频繁切页的封面）；静态一次性图不需要。
7. **不是所有列表都有图**（有的列表只有文字行）→ 没封面的行**别调** `cache()`（空路径会被计入 `fails()` 并 warning）。
8. 组件里没有 `#ifdef` 平台分支，**平台名不出现在组件代码里**（`_WIN32` 只用来选锁实现：设备 pthread / PC std::mutex）。

## 6. 真机验收口径（照这个量）

1. **解码次数（首选，最硬）**：`loads()` 增量 = 解码次数。
   改前：回页一次 `hits=0 / loads=8`；改后：`hits=8 / loads=0`。
   没有读数接口时，用临时埋点量 `setBackgroundPic()` 前后（量完**必须删掉**）。
2. **UI 线程耗时**：同一操作、同一台板、改前后各一次，量「回页合计 ms」（本工程口径 524 → 206 ms）。
3. **内存**：`cat /proc/<pid>/status | grep VmRSS`，缓存 8~40 张时应与改前同量级（本例 ≈ 8964 kB）。
4. **画面**：改前后像素级 diff（`tools/ui_tools/ui_diff.py ... --tol 2`）应**只差动了的地方**；
   列表封面这类改动理想情况是「零像素差」。
5. **别忘反向验证**：搜索/换批场景要专门验一次**不串图**（见 §2.3）。
